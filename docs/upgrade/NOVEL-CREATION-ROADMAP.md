# 小说创作体验优化路线图

> 后续交接版本：[InkWeaver 1.1.0 完整功能图与开发交接书](INKWEAVER-1.1.0-FULL-FEATURE-MAP.md)。该文完整覆盖本稿，并增加持续叙事功能、DSH 插件升级及发布验收。用户已确定全部路线图功能完成后再发布 1.1.0；本稿阶段编号仅保留为开发顺序参考。

日期：2026-09-06。状态：基于当前源码的后续设计建议，本文不表示所列功能已经实现或通过运行验收。范围：桌面应用；独立 DSH 插件不在本轮实施范围。

## 目标与现状

目标是让连续章节保持现场、情绪与因果的延续，让长篇写作能追踪早期事实，并改善人物资料整理和关系图使用体验。

当前已具备 SQLite 项目事实、结构化角色名单、前章结尾输入、近章摘要、定稿连续性投影、叙事线索、工作流会话保护和模型生成预算。后续优先扩展这些机制。

源码证据：

- `src/services/workflows/commands/generate-draft.command.ts`：已有前章定稿结尾输入；近章窗口为 5，摘要与事实总预算约 3000 字符，事实预算 1500 字符、候选最多选 12 条。输入前文不等于已经验证阅读衔接质量。
- `src/shared/consistency-preflight.ts`：确定性检查目前主要识别已死亡角色仍被蓝图安排出场，尚不能代表完整长篇一致性检查。
- `src/services/workflows/commands/finalize-chapter.command.ts`：已有新人物发现和状态更新，但相关提取输入只使用正文前 5000 字符，新人物许多资料字段为空。
- `src/components/editor/RelationshipGraph.tsx`：标签按边中点纵坐标排序，通过全局 lastLabelY 累积向下避让；不检查横向重叠、不限制偏离所属边的距离。这是标签远距离偏移的明确机制，其他坐标问题仍需浏览器复现确认。

## A. 章节交接与阅读连续性

每章定稿后形成可编辑的交接记录：时间、地点、视角、在场人物、未完成动作、即时目标、情绪及原因、伤势或物品限制、待回应悬念。记录绑定定稿 ID、正文哈希和原文证据。

下一章选择承接方式：紧接现场、跨时段、换地点、换视角。蓝图描述本章要推进什么，交接记录描述当前故事停在哪里，两者发生冲突时先向作者解释。

生成流程：读取交接与前章结尾 → 确定承接方式 → 写稿 → 对照相邻章节检查 → 展示局部修改建议。允许作者直接生成，不强制增加每章审批步骤；修改正文仍通过现有修稿和差异确认流程。

新增“检查章节衔接”入口，指出重复介绍、情绪重置、未解释的时间地点变化、动作中断及悬念遗失。默认只建议修改开头或必要过渡段。切视角、倒叙和延迟回应本身不算错误。

代码落点：generate-draft.command.ts、finalize-chapter.command.ts、prompt-builder.ts、ChapterCreationDialog.tsx、DraftEditor.tsx；新增交接共享契约、数据库迁移与 Repository。

验收：使用紧接、跨日、换视角、延后兑现四类章节对；同模型同蓝图对比前后生成，匿名评价承接自然度、重复背景、情绪延续。模型评分仅作辅助，不以请求成功代替质量验收。

## B. 长篇事实与分层记忆

将上下文分为全书固定设定、阶段剧情、角色事件事实、即时现场。按当前章节相关性选取完整记录，避免直接切断拼接后的文本。关键身份和世界规则需要独立优先级，不能仅因发生较早被挤出。

事实记录包含主体、属性或事件、来源定稿、证据、有效章节范围、确认状态和替代关系。支持历史查询：第 12 章获得钥匙、第 18 章转交他人，第 15 与第 20 章应得到不同答案。

增加角色知情范围，区分世界事实、读者已知、角色已知、角色误信。对推理、传闻、梦境、比喻和否定句保持候选状态，不能直接当成权威事实。

检查先运行确定性规则，再按需调用模型审查因果、动机和复杂设定。所有发现都附来源；支持作者记录“有意安排”。AI 新提取内容先形成候选，人工确认后才能改变权威记录；作者已有设定不得被重建覆盖。

代码落点：finalized-continuity.ts、consistency-preflight.ts、summary-repository.ts、narrative-thread-repository.ts、generate-draft.command.ts、ReviewReport.tsx。

验收：至少 100 章固定样本，植入物品转移、伤势恢复、身份揭露、秘密传播与早期规则案例；测量检索覆盖、误报、漏报、输入体积和延迟。修改来源正文后相关投影必须标记过期，重建可恢复且保留作者确认。

## C. 全文人物卡提取

入口覆盖选中文字、当前章节、多章和导入文本。按场景或段落分块处理全部输入，使用少量重叠保持跨块指代，记录每块进度与来源哈希。

流程：提取人物提及与证据 → 识别姓名/别名/称谓 → 匹配已有角色 → 形成新建、更新、身份不确定候选 → 逐字段预览 → 作者确认 → 原子提交。

人物卡区分稳定资料与阶段状态。未提及的字段留空；推断单独呈现。预览显示原值、建议值、证据，默认保护作者手工填写值。人物身份不明确时不得自动合并；关系端点必须在最终名单中存在。

复用 character-roster-repository.ts 的版本检查和原子提交。为别名与身份匹配设计稳定角色 ID 迁移，迁移时保留现有姓名引用并验证全部蓝图和关系引用；不要一次直接更换主键。

代码落点：character-roster.ts、character-roster-repository.ts、character-store.ts、CharacterEditor.tsx、ImportNovelDialog.tsx；新增可恢复提取任务和候选预览。

验收：全文后半段出现人物、一人多称谓、同名不同人、回忆、传闻、否定句、重复提取、取消和重启恢复。相同输入不重复建卡，待确认内容不改变现有人物事实，来源变化后不能应用旧候选。

## D. 关系标签定位修复

先建立能复现标签累积下移的图谱样本。每个标签锚定自身连线，在中点附近尝试有限候选位置；按实际文字矩形检查碰撞，设置屏幕像素下的最大偏移。放不下时隐藏低优先级标签，通过悬停或选中显示详情，必要时加短引导线。

统一内容坐标、画布像素和 CSS 像素转换，绘制、鼠标命中、节点拖拽、悬浮提示使用同一套变换。不能只修改某个乘二系数而忽略其他调用。

代码落点：RelationshipGraph.tsx；建议把坐标转换、边几何与标签布局拆成可独立验证的纯函数，界面保留交互调度。

验收：20/100/200 人样本，不同缩放、拖拽、窗口尺寸与像素密度；直接测量标签到所属边距离和命中位置。增加交叉边、横向分离标签、枢纽节点案例，并检查画布停止模拟后仍正确绘制。

## E. 关系图可用性

默认全局概览，选中人物后进入一跳关系聚焦。增加姓名/别名搜索、本章人物过滤、关系类型过滤、固定节点位置和关系详情侧栏。布局位置属于项目展示偏好，不属于人物事实。

同一对人物可有多种有向关系；“甲暗恋乙”和“乙信任甲”需分别表达。全局图减少文字，详情面板展示完整关系、证据和最近变化。后续增加势力分组及按章节回看关系；历史视图依赖 B 的事实时间范围和 C 的稳定身份。

验收：作者能从大型图谱快速找到指定人物、查看邻居、识别关系方向、跳转证据；过滤与布局操作不修改小说事实，保存位置后重新打开保持稳定。

## F. 配套功能

- 改稿影响分析：修改旧章节后列出受影响摘要、人物状态、伏笔与可能相关后续章节；依赖精确来源优先，模型语义判断作为待检查建议，不自动重写后续正文。
- 伏笔兑现面板：显示首次埋设、最近推进、目标回收范围和证据，重建不能覆盖人工计划。
- 节奏与重复检查：重复开场、重复人物介绍、类似结尾、事件未造成处境变化；提供原文对照，由作者判断。
- 项目快照恢复：批量操作和迁移前提供一致的 SQLite 备份及必要文件清单；恢复后校验身份、正文和附件，再重建可再生索引。不要在数据库写入中直接复制单个 db 文件。
- 上下文可见性：作者可查看本章采用了哪些交接、事实和来源，以及哪些资料未加载；正常写作界面只显示可操作提示。

## 实施顺序与依赖

| 阶段 | 可交付内容 | 前置依赖 |
| --- | --- | --- |
| P0 | 标签定位修复、真实章节对评测基线 | 当前图谱与章节样本 |
| P1-A | 章节交接、承接方式、衔接检查 | 定稿快照和现有修稿流程 |
| P1-B | 全文人物候选提取、确认合并 | 现有角色名单提交；稳定身份渐进迁移 |
| P1-C | 图谱搜索、过滤、局部聚焦、位置固定 | 标签修复 |
| P2 | 分层记忆、历史事实、知情范围、过期重建 | 来源与身份契约 |
| P2 配套 | 改稿影响提示、项目快照 | 历史事实依赖与恢复验证 |
| P3 | 关系时间轴、阵营、节奏检查 | 前述数据基础与阅读质量评测 |

暂不承诺日历工期。先完成 P0 的复现和样本基线，再按迁移、模型调用、界面和测试范围估算各阶段。

## 共同实现约束

继续遵守 docs/adr 中的项目会话、外部文件授权、结构化角色事实源、定稿投影和人工计划边界。新增后台任务必须冻结项目会话与输入版本，提供取消、成本预估、恢复及过期结果拒绝。已有重要作品先备份，迁移保持可回退。

功能开发的完成证据包括领域测试、相应浏览器交互验证和真实文本质量评估。方案文档完成、类型检查通过或模型正常结束，均不代表以上功能已经交付。
